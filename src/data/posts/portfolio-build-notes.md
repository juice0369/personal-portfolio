## 起点：一个只能改代码的静态页面

最早的作品集是一张静态页：想改一句自我介绍，就要打开编辑器、改 HTML、重新部署。项目细节也没地方放，只能塞进一行描述里。

真正的痛点是**内容的维护成本**，不是页面本身好不好看。所以这次的目标很明确：让"改内容"变成在浏览器里点几下的事。

## 为什么不引入后端

按常规思路应该加一个数据库和一套接口。但这里有两个约束：

1. 站点只需要我自己维护，没有多用户问题；
2. 部署必须是零成本的静态托管。

于是把数据放回浏览器就成了最合理的方案：结构化内容存 `localStorage`，头像和简历这类二进制文件存 `IndexedDB`。

## 唯一真源：一份 Schema

最影响长期可维护性的决定，是把 Zod schema 当作唯一真源：

| 用途         | 之前           | 现在               |
| ------------ | -------------- | ------------------ |
| 类型         | 手写 interface | `z.infer` 推导     |
| 表单校验     | 单独写一遍     | 复用同一份 schema  |
| 本地数据校验 | 基本没有       | 读取时 `safeParse` |
| 导入校验     | 没有           | 复用同一份 schema  |

四种用途共用一套规则，就不会出现"表单通过了，但读出来报格式错误"的情况。

## 明确接受的取舍

导出 JSON 时不含头像与简历的二进制内容，好处是不需要引入 zip 依赖，代价是换设备导入后要重新上传这两个文件。这个限制在界面和文档里都写清楚了，而不是留给用户去猜。
